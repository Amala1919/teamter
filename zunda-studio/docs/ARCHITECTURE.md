# アーキテクチャ

## 1. 全体構成

```
┌─ Electron main process (Node.js) ───────────────────────────┐
│  VoiceEngineManager   VOICEVOX ENGINE の起動・停止・死活監視  │
│  SynthesisService     音声合成 + モーラ情報取得 + キャッシュ   │
│  PsdService           PSD解析・パーツのビットマップ化         │
│  MediaService         ffprobe/ffmpeg: メタ情報・プロキシ生成  │
│  ExportService        音声ミックスと最終mux、進捗通知         │
│  ProjectStore         プロジェクトJSONの原子的な読み書き      │
│  AiService            会話AI/編集AIの呼び出し(CLIプロバイダ)   │
│  LiveSessionService   録画中の会話の記録(JSONL追記)とOBS連携  │
└──────────────── IPC (preload の contextBridge) ─────────────┘
┌─ Electron renderer process (React + TypeScript) ────────────┐
│  ProjectState (zustand)  プロジェクトの単一の真実            │
│  CommandBus              すべての変更はコマンド経由 + undo    │
│  Compositor              Canvas による合成描画(唯一の実装)   │
│  PreviewPlayer           Compositor をリアルタイム駆動        │
│  FrameExporter           Compositor を決定論的に1コマずつ駆動 │
│  UI: 台本 / タイムライン / プレビュー / インスペクタ / チャット │
└─────────────────────────────────────────────────────────────┘
```

Electronを選ぶ理由は、後述する書き出し方式がWebCodecs(`VideoDecoder`/`VideoEncoder`)に依存するためである。Tauriは各OSのWebViewに依存するためWebCodecsの可用性が揃わない。

## 2. 設計の柱

### 2.1 すべての変更はコマンドを通す

手動編集・AIチャット・自動下書きという3つの入力経路があるが、これらを別々に実装すると整合性が保てない。そこで**プロジェクトへの変更は必ず「コマンド」という直列化可能なオブジェクトとして表現する**。

```
UI操作 ─┐
AIチャット ─┼→ Command[] → CommandBus → ProjectState → Compositor
自動下書き ─┘                   ↓
                            UndoStack
```

この構造から以下が自動的に得られる。

- undo/redo は CommandBus に集約され、UIにもAIにも個別実装が不要
- AIの編集は「コマンド列の提案」となり、適用前に差分として提示できる(A-1)
- AIの一連の編集を1つのトランザクションとして扱えるので、まとめてundoできる(A-7)
- コマンド列を記録すれば編集操作を再現でき、不具合の再現とテストが容易になる

コマンドの仕様は [AI_EDIT_PROTOCOL.md](AI_EDIT_PROTOCOL.md) で定義する。AI専用のコマンド体系は作らず、UIが使うコマンドと同一のものをAIに公開する。

### 2.2 プレビューと書き出しは同一のレンダラを使う

「プレビューでは良かったのに書き出したらズレた」を構造的に起こさないため、合成描画の実装は `Compositor` 1つに限定する。`Compositor` は次の純粋な関数として定義する。

```
render(project, timeMs, targetCanvas) → void
```

これを**リアルタイムに呼べばプレビュー、タイマーではなくフレーム番号で順に呼べば書き出し**になる。時刻に依存するもの(まばたきのタイミング、振動エフェクトの乱数)は現在時刻や乱数を直接参照せず、`timeMs` とプロジェクト内のシード値から決定論的に導出する。これにより非機能要件の決定性が保証される。

### 2.3 映像の書き出し経路

| 工程 | 手段 |
| --- | --- |
| 素材動画のフレーム取得 | `<video>` 要素をフレーム単位でシークし、描画可能になったフレームを使う |
| 合成 | `Compositor`(Canvas2D。負荷が問題になればWebGLに差し替え可能な内部境界を設ける) |
| 映像のエンコード | 合成したフレームを main process の ffmpeg の標準入力へ流す(libx264) |
| 音声のミックス | main process の ffmpeg(ボイス群 + BGM + SE + ダッキング) |
| 多重化 | 同じ ffmpeg の呼び出しで映像と音声をまとめて mp4 にする |

音声をffmpegに任せるのは、多数のボイスアイテムの配置とミックスがffmpegのフィルタグラフで正確かつ高速に書けるためである。一方で映像はフレームごとの立ち絵アニメーションを持つため、フィルタグラフでは表現しきれない。そこで映像はCompositorが1コマずつ描き、それをffmpegに渡す。

当初はWebCodecsの `VideoEncoder` を本命にしていたが、最初の実装では**ffmpegの標準入力へ流す方式を採る**。どの環境でも同じ結果になり、テスト環境でも実物のffmpegで検証できるためである。フレームの受け渡しは `FrameSink` インターフェースで抽象化してあり、速度が問題になった時点でWebCodecs(ハードウェアエンコード)の実装を追加して差し替える。

### 2.4 音声合成の統合

VOICEVOX ENGINEはHTTPサーバ(既定ポート50021)として動作する。main processがこれを子プロセスとして起動し、ライフサイクルを管理する。

```
起動時: 既存の起動済みエンジンを検出 → なければ同梱エンジンを起動 → /version で死活確認
合成:   POST /audio_query  → AudioQuery(モーラ列と長さを含む)
        AudioQuery を調整 → POST /synthesis → wav
```

`/audio_query` が返す `AccentPhrase.moras[]` は各モーラの `vowel`(a/i/u/e/o/N/cl/pau)と `consonant_length` / `vowel_length` を持つ。**この情報をそのまま口パクのタイムラインに変換できる**ため、音量解析による推定より正確な口パクが追加コストなしで得られる。

```
moras + speedScale + prePhonemeLength → LipSyncTrack { timeMs, vowel }[]
```

母音に対応する口パーツを持たない立ち絵(開閉2〜3段階のみ)向けには、母音を開口度にマップしてから段階パーツに割り当てる。

エンジンはVOICEVOX以外(AivisSpeech、COEIROINK)もほぼ同一のAPI形状を持つため、`VoiceEngine` インターフェースで抽象化し、実装として `VoicevoxCompatibleEngine` を1つ持つ構成にする。

合成結果は `hash(engineId, speakerId, text, params)` をキーにディスクキャッシュする。セリフを1文字直すだけで全再合成が走るのを防ぐ。

### 2.5 立ち絵(PSD)の扱い

PSDの解析は main process で `ag-psd` を用いて行い、レイヤーツリーを取得する。レイヤー名の命名規約(`*` / `!` 接頭辞)には依存させず、次の流れでパーツを確定する。

```
PSD読込 → レイヤーツリー → 役割の自動推定(名前のヒント) → ユーザーが確認・修正 → キャラクター設定に保存
```

役割は `eye` / `mouth` / `eyebrow` / `body` / `other` と、パーツ内の並び順(まばたき・口パクでは開→閉の順序が意味を持つ)を持つ。確定した各パーツは描画のたびにPSDを解析し直さないよう、PNGとしてキャッシュディレクトリに書き出し、レンダラはそれを読む。

### 2.6 ライブモード(録画中の会話記録)

録画中にAIと会話し、その内容を録画上の時刻付きで記録する。編集用のウィンドウとは別の、常に前面に出せる小さなウィンドウとして実装する。ゲームをプレイしながら使うため、編集UIをそのまま流用しない。

```
┌─ ライブウィンドウ(常に最前面、小さい) ────────┐
│  会話ログ(直近のみ)                          │
│  [押しながら話す] または テキスト入力          │
│  [目印を打つ]                                │
└──────────────────────────────────────────────┘
      ↓ 発言ごとに追記保存
  セッションログ(JSONL) ── 編集時にプロジェクトへ取り込む
```

**時刻の対応付け**が設計の要点である。アプリは録画そのものを行わない(OBS等を使う)ため、セッション内の相対時刻と録画上の時刻を対応付ける必要がある。

| 方法 | 内容 | 優先度 |
| --- | --- | --- |
| OBS WebSocket | 録画の開始・終了イベントと出力ファイル名を受け取り、自動で対応付ける | 本命 |
| 手動調整 | 発言を1つ選び、プレビューを合わせたい瞬間に移動して「ここに合わせる」を押す | 常に必要 |

記録は相対時刻(セッション開始からのms)で保存し、録画との対応は `offsetMs` 1つで表す。こうすると、あとからずれを直すときに全発言を書き換えずに済む。

記録は**発言ごとにJSONL形式で追記保存する**。プレイ中にアプリが落ちても、それまでの会話が失われないようにするためである。プロジェクトへの取り込みは編集時に行う。

音声入力は押しながら話す方式とし、文字起こしはローカル(whisper.cpp)を既定とする。プレイ中の発話をクラウドへ送り続けるのは、プライバシーと遅延の両面で望ましくない。AIの返答を音声で返す場合は、出力先デバイスを選べるようにする(録画に混ぜたくない場合があるため)。

ライブモードのAIは、相方と同じペルソナを使う。録画中の会話と動画内の掛け合いで人格が変わると、台本に採用したときに違和感が出るためである。一方でモデル設定は別に持つ(プレイ中は速さを優先する)。

### 2.7 大容量素材への対応

数時間の録画を扱うため、次の方針を採る。

- 素材ファイルは読み込み時にメタ情報(`ffprobe`)のみ取得し、中身はメモリに載せない
- 編集時のプレビューには低解像度プロキシ(例: 540p)を使い、書き出し時のみ原本を参照する
- タイムラインの波形表示は事前に生成したピークデータを使い、毎回デコードしない
- プロキシ・波形・音声キャッシュはプロジェクトファイルとは別のキャッシュディレクトリに置き、破棄しても再生成できるものとして扱う

### 2.8 AIプロバイダ

会話AIと編集AIは、どちらも `LlmProvider` インターフェースの実装を通して呼び出す。

```
LlmProvider
  detect()        CLIの有無・バージョン・ログイン状態
  listModels()    選択肢として出すモデル一覧
  generate(req)   システムプロンプト + 会話 + (任意)JSONスキーマ → テキスト / 構造化出力

実装
  ClaudeCodeCliProvider   claude -p を隔離モードで起動(サブスクのログインを使う)
  OpenCodeCliProvider     opencode run を専用エージェント定義付きで起動
  (将来) AnthropicApiProvider, ローカルLLM など
```

**どちらもローカルCLIを子プロセスとして起動する**方式を採る。ユーザーが既にログインしている各CLIの認証をそのまま使えるので、アプリは資格情報を一切持たない。また OpenCode Go はモデルごとにAPI形式(Chat Completions / Messages / Responses)が異なるが、OpenCode CLI がその差を吸収してくれる。

CLIはどちらもコーディングエージェントなので、そのまま呼ぶとファイル操作やシェル実行のツールを持ち、ユーザーの設定(CLAUDE.md、フック、MCP等)も読み込む。台本生成には不要なうえ、遅く、副作用もありうる。そこで次のように隔離して呼ぶ。

| | Claude Code | OpenCode |
| --- | --- | --- |
| 作業ディレクトリ | アプリ専用の空ディレクトリ | 同左 |
| ツール | `--tools ""` で全て無効 | 専用エージェントの `permission` を全て `deny` |
| システムプロンプト | `--system-prompt-file` で完全に置き換える | 専用エージェントの `prompt` |
| ユーザー設定 | `--safe-mode`(フック・CLAUDE.md・MCP等を読まない) | `--pure`、`OPENCODE_DISABLE_CLAUDE_CODE=1` |
| 履歴 | `--no-session-persistence` | (セッションはCLI側に残る) |
| 構造化出力 | `--json-schema` を使い `structured_output` を読む | 出力をJSONとして抽出し、アプリ側でスキーマ検証する |
| 入力 | プロンプトは標準入力で渡す(コマンドライン長の制限を避ける) | 同左 |
| 認証 | `--bare` は付けない(付けるとサブスクのログインが使われない) | CLIの `/connect` 済みの認証を使う |

`--bare` を付けないことは特に重要である。`--bare` はAPIキーでの認証しか読まないため、サブスクのログインが使われなくなる。

構造化出力が必要な処理(編集コマンドの生成、返答候補と表情の同時生成)では、スキーマを `zod` で1箇所に定義し、そこから (a) 型、(b) 実行時の検証、(c) CLIに渡すJSONスキーマの3つを導出する。AIの出力は必ずアプリ側でも検証し、失敗したら1回だけ再試行する。

役割とモデルの割り当ては次の3層で決まる。

```
その呼び出しで明示されたモデル(再生成時の一時的な切り替え)
  ↓ なければ
プロジェクトの会話AI設定(会話AIのみ。「今回の相方」)
  ↓ なければ
アプリ設定の役割ごとの既定値
```

生成した結果には常に `{ providerId, model }` を添えて返し、ボイスアイテムやライブの発言に記録する。

### 2.9 テスト用ホスト

main process のサービスはElectronに依存しない純粋なNodeモジュールとして書き、IPCのハンドラ表を介して公開する。Electronでは `ipcMain.handle` にこの表を登録し、開発・テスト時は同じ表をHTTPで公開する小さなホストを立てる。レンダラは `window.zunda` がElectronのpreloadから来たものか、HTTPホスト向けのものかを意識しない。

```
                 ┌─ Electron: ipcMain.handle ─ preload(contextBridge) ─┐
ハンドラ表 ───────┤                                                      ├→ レンダラ
(Node の純粋な   └─ テスト用ホスト: HTTP POST /ipc/:channel ─ fetch ────┘
  サービス群)
```

これにより、Electronを起動できない環境でも、**本物のサービス(音声合成、書き出し、AI呼び出し)を本物のレンダラから動かす**E2Eテストが書ける。外部依存(VOICEVOX、各CLI、OBS)は模擬サーバー・模擬CLIに差し替える。ファイル選択ダイアログのようなElectron固有の機能だけは、テスト用ホスト側でキューに積んだ応答を返す。

## 4. プロセス間通信とセキュリティ

- `contextIsolation: true` / `nodeIntegration: false` を維持し、レンダラにNodeの権限を与えない
- レンダラが使える操作は preload で明示的に列挙したものだけに限る
- ユーザーが指定したファイル以外を読み書きしない。パスはmain側で正規化し、プロジェクトディレクトリとキャッシュディレクトリの外への書き込みを拒否する
- AIの認証は各CLIのログインに任せ、アプリは資格情報を保持しない。CLIに渡す引数は検証済みの値(モデルIDは許可文字のみ)に限り、本文は標準入力とファイルで渡す
- AIに渡すのはプロジェクトの構造と台本テキストに限り、素材ファイルの中身を無断で送信しない

## 5. 状態管理

プロジェクトの状態はレンダラの zustand ストアが単一の真実として持つ。更新は必ずコマンド経由とし、ストアを直接書き換えるコードを書かない(ESLintルールで機械的に禁止する)。

保存は「ストアのプロジェクトをシリアライズしてmainに渡す」だけとし、一時ファイルへ書いてから `rename` することで原子性を担保する。

## 6. テスト方針

| 対象 | 方法 |
| --- | --- |
| コマンドの適用結果 | ユニットテスト。プロジェクト → コマンド → 期待するプロジェクト |
| undo/redo | 任意のコマンド列を適用しundoで元に戻ることを検証する |
| 口パク生成 | VOICEVOXの実レスポンスを固定データとして持ち、モーラ列 → 口パクタイムラインを検証する |
| 字幕の組版 | 自動改行の結果を検証する |
| Compositor | 代表的なプロジェクトを固定時刻で描画し、基準画像と比較する(ゴールデンテスト) |
| AIのコマンド生成 | 生成されたコマンドがスキーマに適合し、適用可能であることを検証する。LLM応答は固定データで代替する |
| AIプロバイダ | 模擬CLI(引数と標準入力を記録し、決まった出力を返すスクリプト)を実際に子プロセスとして起動し、引数の組み立てと出力の解釈を検証する |
| E2E | テスト用ホスト + ビルド済みレンダラ + Playwright(Chromium)で、台本入力から書き出しまでを通す |
| 書き出し | 短いプロジェクトを実際に書き出し、尺・解像度・音声の有無を検証する |

AIの出力は本質的に不確定なので、テストは「生成されたコマンドが妥当か」の検証に限定し、文章の内容そのものは検証しない。

## 7. 未決の技術課題

以下は実装時に検証して決める。

1. Canvas2Dで1080p30・立ち絵2体+字幕のリアルタイム合成が成立するか。不足する場合はWebGLに切り替える
2. WebCodecs `VideoEncoder` の各OSでの可用性とハードウェアエンコードの利用可否
3. VOICEVOX ENGINEの配布形態(公式配布物のダウンロードとバージョン固定の方法)
4. `ag-psd` が実在の配布立ち絵(数百レイヤー、クリッピングマスクやレイヤー効果を含む)を正しく解釈できるか
5. 長尺録画に対するプロキシ生成の所要時間が許容範囲に収まるか
